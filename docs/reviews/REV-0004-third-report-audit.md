# REV-0004 — Третий отчёт: аудит поиска C++ vtable

**Дата:** 2026-10-26. **Статус:** проверка предоставленной сводки, не повторный анализ бинарника. Первичные `EXP-0017-vtable-candidate-triage.md`, `vtable_assignment_scan.py`, raw output и EXE здесь недоступны.

## Подтверждено только на уровне отчёта

Новый индекс охватывал **72 437 функций**, тогда как прежний автоанализ сообщал **72 925**; разность **488**. Сканер нашёл **10 002** инструкции прямой записи, **4 267** адресов-кандидатов и **1 176** записей, удовлетворяющих 11-слотовому структурному фильтру (**27,56%** всех кандидатов). Это доля прошедших фильтр, а не вероятность правильной атрибуции vtable. Без двух полных списков entry VA причину разницы 488 установить нельзя.

## Критическое уточнение: независимые классы

- `DisGFxMoviePlayerPowerWheel.OnSelectionChanged(int)` → receiver `+0x1F0`, exec wrapper `0x009F8290`.
- `DishonoredPlayerController.Dis_SelectPower(int)` → receiver `+0x560`, exec wrapper `0x009EE630`.

**Два смещения относятся к разным получателям вызова**. Неподходящий `+0x560` не исключает таблицу для PowerWheel; неподходящий `+0x1F0` не исключает её для Controller. Каждую комбинацию (VA таблицы, класс, слот) оценивать отдельно.

## Методологические риски

1. Запись адреса функции в первый DWORD объекта не тождественна установке vptr: обычно записывается **адрес массива** указателей, а не адрес функции.
2. «11/11 указателей на функции» не устанавливает владельца и может исключать валидные vtable с purecall/thunks/неразмеченными кодовыми адресами.
3. Соседство слотов не доказывает начало таблицы, особенно при наследовании и multiple inheritance.
4. Декомпилятор может неточно восстановить ABI, количество аргументов, скрытый `this` и побочные эффекты.
5. В третьем ходе EXE не был повторно найден и хеширован — новая бинарная идентичность не подтверждена.

## Проверяемая причина разницы 488 функций

По официальной документации Ghidra API `FunctionManager.getFunctionCount()` включает **external** функции, а `getFunctions(true)` перечисляет только **non-external** функции; `getExternalFunctions()` позволяет посчитать разницу отдельно. Поэтому отчётные 72 925 против 72 437 могут различаться ровно на 488 external entries — **если** старый счётчик и новый сканер использовали именно эти методы в одной базе. Это гипотеза, не доказанный факт. Скрипт `tools/Exp0018FunctionCountAudit.java` экспортирует все три показателя и сравнит количество внешних функций с 488. [API Ghidra](https://ghidra.re/ghidra_docs/api/ghidra/program/model/listing/FunctionManager.html).
